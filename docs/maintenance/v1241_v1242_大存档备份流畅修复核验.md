# v1241 和 v1242 大存档备份流畅修复核验

## 现场结论

用户提供的 v1239 诊断在 backup-wait-boot 后立即进入 backup-copy，随后记录 7,640 毫秒、12,919 毫秒和 36,005 毫秒事件循环停顿，之后出现 pagehide 且 persisted=false。记录中没有后续 backup-serialize、backup-image-read 或 backup-download，因此这次卡顿发生在整份存档复制阶段，文件保存、Service Worker 和那一张损坏的页面图片都没有进入可疑链路。

诊断中的 MacIntel 来自 iPhone Safari 的桌面级 User-Agent。standalone=true、402 x 812 视口和 3 倍像素比表明这是已添加到主屏幕的 iPhone 网页应用，不是 Mac 浏览器。全部脚本均为 v1239，排除了新旧脚本混载。pagehide 只能证明文档被销毁；结合 36 秒主线程停顿可判断 WebKit 页面进程承受了明显压力，但仅靠网页诊断不能证明是系统强杀，也不能排除用户主动关闭或刷新。

## 根因与修改

v1238 至 v1239 的完整备份会先递归复制整个状态树。每进入数组都执行 Object.keys 建立完整键表，再创建同样大小的新数组和对象；十万级导入存档会因此同时占用原状态、数组键表和复制状态。旧实现虽每 1,024 个属性尝试让出主线程，但完整数组键表在第一次让出之前已经同步创建。

网页 v1241 和私人内置源码 v1242 改为直接分段读取当前存档。进入对象时固定键列表，进入数组时只固定长度并按下标读取，不再创建十万级数组键表或整份状态副本。序列化路径改用共享的可变路径栈，减少每个字段的临时数组；每 64 个工作单元检查一次 8 毫秒时间预算并主动让出主线程。图片、三类 IndexedDB 聊天存档、缺图失败、导入回滚和最终 JSON 格式保持原规则。

公开网页使用 v1241 和独立缓存身份 v1241-backup-streaming-1。私人内置源码使用 v1242 和 v1242-backup-streaming-1，私人 iOS 仍为 1.0.356（356），原生桥仍为 38。本轮不制作私人安装包。

## 验证

- 新增 116,736 项数组回归。旧实现会因尝试枚举完整数组键表而失败，新实现成功导出，数组长度和首尾记录一致。
- WebKit 真实页面夹具包含 116,736 条聊天和 48 张媒体，导出文件 51,449,495 字节，用时 14,920 毫秒；导入、保存和重启恢复后仍为 116,736 条，最大事件循环间隔 195 毫秒，页面错误为 0。
- Edge 真实页面夹具使用相同数据，导出文件 51,449,425 字节，用时 3,298 毫秒；导入、保存和重启恢复后数据一致，最大事件循环间隔 280 毫秒，页面错误为 0。
- 备份专项、版本和诊断共 33 项通过；Windows 全仓 1,831/1,831 通过。
- 网页与私人内置真实入口的授权开关、已有记录、过滤输出、普通回复、手动回复、自动查手机、忙碌释放和重启恢复矩阵通过，两端页面错误均为 0。模型 HTTP 使用测试服务。
- 三份维护 DOCX 的原有 5,127 个段落逐项保持，分别只追加 5 个段落，OOXML 和 ZIP 结构完整。工作区未提供 LibreOffice soffice.exe，无法完成页面 PNG 视觉渲染，本轮不把结构检查表述为视觉验收。

桌面 WebKit 和 Edge 测试不是用户真实 iPhone 或华为设备。线上部署完成后仍需在原浏览器用真实大存档点击一次“导出备份（文件）”，并复制新版诊断确认不再出现 backup-copy 和秒级事件循环停顿。
