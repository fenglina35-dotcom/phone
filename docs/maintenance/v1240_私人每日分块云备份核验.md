# v1240 私人每日分块云备份核验

## 范围与版本

- 仅发布私人源码候选：私人内置页 v1240、iOS 1.0.356（356）、原生桥 38。
- 公开网页 `app.js`、网页入口与 `sw.js` 保持 v1239，本轮不重新部署网页。
- 保留私人账号、恢复、网页镜像、聊天、角色、图片、HomeKit、Screen Time 和既有原生能力。

## 已确认事实

- 用户截图中的私人安装包为 v1231 / 1.0.354（354），最近云备份显示 54.0 MB；点击“立即备份本机”后出现“原生请求超时：account.backup.upload”。
- 同一页面“刷新状态”能正常返回。它证明手机号登录凭证和账号状态的小请求可用，不能证明几十 MB 备份上传链路可用。
- 旧网页函数把完整 `snapshot` 一次性交给 `account.backup.upload`。旧原生桥再执行整份 `JSONSerialization.data`、SHA-256 和 RPC body 组装；普通原生网络请求超时为 18 秒，网页等待大多数原生请求为 60 秒。
- iOS247 曾因排查 WebContent 压力而暂停自动全量云备份，保留手动备份。那是诊断性降压，不是已经证明的最终根因。

## 原因判断

代码证据足以确认旧实现存在两个确定缺陷：大对象在网页桥和原生层重复展开，以及大上传沿用短超时。两者都能解释 54 MB 级备份“账号刷新正常、备份超时”的差异，也会增加页面和 WebContent 的内存压力。

尚不能把它写成用户真机故障的唯一根因：Windows 无法取得该 iPhone 当次 WebContent 内存、网络和服务端耗时，也没有完成真实 iPhone 的新链路上传。结论是“修复了可复现的结构性缺陷，等待真机验证”，不是“已经证明所有卡顿都由备份导致”。

## 修改

- 网页端使用现有分段备份生成器创建 Blob，每次只把 192 KiB 交给原生桥。
- 原生桥新增 `account.backup.file.begin/chunk/commit/abort`。分块严格校验账号、令牌、偏移、单块大小和总字节数，按顺序写入应用临时目录；提交时补齐 RPC JSON 外壳并通过 `URLSession.upload(for:fromFile:)` 上传文件。
- 上传请求超时改为 180 秒、资源总时限 600 秒；`SmallPhoneNative.request` 对提交阶段等待 660 秒。2026-09-21 复查发现业务层 `privatePhoneAccountCall` 仍沿用 120 秒默认值，会早于原生上传返回；候选修复把提交调用显式放宽到 720 秒。临时文件在成功、失败和中止后删除。
- 只有 HTTP 成功并且 RPC 第一行明确返回 `saved=true` 才向网页确认成功。分块失败、超时、云端拒绝旧修订或账号变化都不写“今日成功”，也不删除旧云备份。
- 首次升级、本地未确认来源或发现云端来自其他设备的新时间时，自动备份停止并等待用户手动确认，避免空存档或旧设备覆盖新备份。
- 每日备份仅在登录、启动图片/存档读取完成、页面位于前台、空闲至少 90 秒、无回复生成和无原生维护任务时尝试；失败 30 分钟后可重试，一天成功一次后停止重复。
- App 关闭时不承诺每天准点执行。Apple 的后台任务接口只允许设置最早开始时间，实际调度由系统决定：[Apple BackgroundTasks earliestBeginDate](https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate)。

## 回归与证据

- 新行为测试：旧整对象桥在设定的大载荷边界失败；新路径按小块发送并成功提交。
- 覆盖分块失败后执行 abort 且不记当天成功、页面隐藏不启动、已有云备份未确认时不覆盖、其他设备云端时间更新后重新阻止自动备份。
- 原生结构测试覆盖四个新动作、账号与偏移校验、262144 字节上限、文件上传、180/600/660 秒时限、RPC `saved` 判定和临时文件清理。
- Edge 与 WebKit 的大存档浏览器回归通过：10,000 条消息、48 张不同图片完整保留，页面错误为 0。该测试验证备份构造和导入，不等于真实手机号云端上传。
- 网页与私人内置页核心聊天回归通过，页面错误为 0。
- 全仓 Node：1830/1830 通过。
- `node --check` 与 `git diff --check` 在打包前执行；包内清单、ZIP CRC、解压后逐字节一致性另行核验。

## 失败尝试与边界

- v1233 至 v1238 主要处理网页文件导出、下载、分段读取和导入时序，不能解决私人 `account.backup.upload` 的原生整对象桥和短网络超时。
- 仅根据“刷新状态成功”判断备份服务正常是错误前提；两者请求体大小、处理阶段和时限不同。
- Windows 无法编译 Swift、签名或替代真实 iPhone。交付物是 Mac 待编译源码覆盖包，不是 IPA；必须在真机验证 54 MB 级立即备份、刷新后的云时间/大小、跨日一次自动备份、失败保留旧备份以及从云端恢复。

## 2026-09-21 补充复查

- 私人 v1274 源码、Mac 源码包和两个入口都包含 `private-cloud-backup.js`；Xcode 主 Target 使用文件夹自动同步，且没有把该文件列为例外。因此现有证据不支持“v1274 源码包漏掉修复文件”。
- 分片提交实际经过 `privatePhoneAccountCall → SmallPhoneNative.request → URLSession` 三层。此前测试只断言后两层 660／600 秒，没有断言第一层实际收到的超时参数，因而漏过 120 秒提前失败。
- 候选修复给 `account.backup.file.commit` 显式传入 720000 毫秒，并新增永久发布门禁，检查组件文件、两个入口、四个动作、原生文件上传、Xcode 资源归属和三层等待关系。专项及永久门禁 240/240 通过。
- 这仍是 Windows 代码证据。当前 v1274 真机的最新提示和诊断尚未取得，不能把 120 秒缺口写成该设备本次失败的唯一原因；Mac 构建和真实 iPhone 54 MB 上传仍需验证。
